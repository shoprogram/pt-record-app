# 認可制御のテスト手順

このドキュメントでは、実装した認可制御（Row Level Security）が正しく機能することを確認するためのテスト手順を説明します。

## 前提条件

1. Supabaseプロジェクトが作成されている
2. `.env`ファイルに以下の環境変数が設定されている：
   ```
   SUPABASE_URL=your-project-url
   SUPABASE_KEY=your-anon-key
   ```
3. マイグレーションが実行されている（`supabase/migrations/001_initial_schema.sql`）

## マイグレーションの実行方法

### Supabase CLIを使用する場合

```bash
# Supabaseプロジェクトをリンク
supabase link --project-ref your-project-ref

# マイグレーションを実行
supabase db push
```

### Supabase Dashboardを使用する場合

1. Supabase Dashboard (https://app.supabase.com) にアクセス
2. プロジェクトを選択
3. SQL Editor に移動
4. `supabase/migrations/001_initial_schema.sql` の内容をコピー&ペースト
5. 実行

## テスト手順

### 1. 準備：開発サーバーの起動

```bash
npm run dev
```

### 2. ユーザーAのテスト

#### 2-1. アカウント作成とログイン

1. ブラウザで `http://localhost:3000/signup` にアクセス
2. ユーザーA用のメールアドレスとパスワードで新規登録
   - 例：`user-a@example.com` / `password123`
3. 登録後、自動的にログインされることを確認

#### 2-2. 患者データの作成

1. 患者一覧ページ（`/`）で「新規患者登録」ボタンをクリック
2. 以下の情報で患者を2名登録：

   **患者A-1:**
   - 患者コード: `A-001`
   - 名前: `テスト患者A-1`
   - 年齢: `45`
   - 性別: `男性`
   - 診断名: `腰痛`

   **患者A-2:**
   - 患者コード: `A-002`
   - 名前: `テスト患者A-2`
   - 年齢: `32`
   - 性別: `女性`
   - 診断名: `肩こり`

3. 患者一覧に2名の患者が表示されることを確認

#### 2-3. 記録の作成

1. 患者A-1の詳細ページに移動
2. 「今日の記録」フォームで記録を作成
3. 保存が成功し、記録一覧に表示されることを確認

#### 2-4. ユーザーAの患者IDをメモ

1. 患者A-1の詳細ページのURLから患者IDをコピー
   - 例：`http://localhost:3000/patients/UUID-HERE` の `UUID-HERE` 部分
2. このIDを後で使用するためメモしておく

#### 2-5. ログアウト

1. サイドメニューの「ログアウト」をクリック

### 3. ユーザーBのテスト

#### 3-1. アカウント作成とログイン

1. `http://localhost:3000/signup` にアクセス
2. ユーザーB用のメールアドレスとパスワードで新規登録
   - 例：`user-b@example.com` / `password456`

#### 3-2. 患者データの作成

1. ユーザーB用の患者を1名登録：

   **患者B-1:**
   - 患者コード: `B-001`
   - 名前: `テスト患者B-1`
   - 年齢: `58`
   - 性別: `男性`
   - 診断名: `膝痛`

2. 患者一覧に**1名のみ**表示されることを確認
   - ✅ **重要**: ユーザーAの患者（A-1, A-2）は表示されない

### 4. 認可制御の検証

#### 4-1. 直接URLアクセスのテスト

1. ユーザーBでログインしたまま、ブラウザのアドレスバーに以下を入力：

   ```
   http://localhost:3000/patients/[ユーザーAの患者ID]
   ```

   （先ほどメモしたユーザーAの患者IDを使用）

2. **期待される動作**：
   - ✅ 404エラーまたは「患者が見つかりません」と表示される
   - ✅ ユーザーAの患者情報は表示されない

#### 4-2. API直接アクセスのテスト

1. ブラウザの開発者ツール（F12）を開く
2. Consoleタブで以下を実行：

```javascript
// ユーザーAの患者一覧を取得しようとする
fetch('/api/patients')
  .then((r) => r.json())
  .then(console.log)
```

3. **期待される結果**：
   - ✅ ユーザーBの患者のみが返される
   - ✅ ユーザーAの患者は含まれていない

```javascript
// ユーザーAの患者詳細を取得しようとする
fetch('/api/patients/[ユーザーAの患者ID]')
  .then((r) => r.json())
  .then(console.log)
```

4. **期待される結果**：
   - ✅ 404エラーまたは空のレスポンス

#### 4-3. 記録作成の認可テスト

1. 開発者ツールのConsoleで以下を実行：

```javascript
// ユーザーAの患者に記録を作成しようとする
fetch('/api/patients/[ユーザーAの患者ID]/records', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    date: '2025-01-10',
    standardEvaluations: { vas: 50 },
    customEvaluations: [],
    note: '不正なアクセステスト',
  }),
})
  .then((r) => r.json())
  .then(console.log)
```

2. **期待される結果**：
   - ✅ 403エラー「この患者の記録を作成する権限がありません」
   - ✅ または404エラー「患者が見つかりません」

### 5. クロスユーザーテスト

#### 5-1. ユーザーAに戻る

1. ユーザーBからログアウト
2. ユーザーAでログイン

#### 5-2. データの確認

1. 患者一覧を確認
   - ✅ ユーザーAの患者2名（A-1, A-2）のみ表示される
   - ✅ ユーザーBの患者（B-1）は表示されない

2. 患者A-1の記録を確認
   - ✅ 先ほど作成した記録が表示される
   - ✅ データが正しく保存されている

## テスト結果のチェックリスト

### セキュリティ要件

- [ ] ユーザーAは自分の患者のみ閲覧できる
- [ ] ユーザーBは自分の患者のみ閲覧できる
- [ ] ユーザーBは直接URLでユーザーAの患者にアクセスできない
- [ ] ユーザーBはAPIでユーザーAの患者データを取得できない
- [ ] ユーザーBはユーザーAの患者に記録を作成できない
- [ ] 各ユーザーは自分の患者のみ一覧に表示される

### 機能要件

- [ ] 新規患者登録が正常に動作する
- [ ] 患者一覧が正しく表示される
- [ ] 患者詳細が正しく表示される
- [ ] 記録の作成が正常に動作する
- [ ] 記録一覧が正しく表示される
- [ ] エラーメッセージが適切に表示される

## トラブルシューティング

### マイグレーションエラーが発生した場合

1. Supabase Dashboardでテーブルが作成されているか確認
2. RLSが有効になっているか確認（Table EditorでRLSのトグルをチェック）
3. ポリシーが正しく作成されているか確認

### 環境変数エラーが発生した場合

1. `.env`ファイルが正しく作成されているか確認
2. `SUPABASE_URL`と`SUPABASE_KEY`が正しく設定されているか確認
3. 開発サーバーを再起動

### 認証エラーが発生した場合

1. Supabase Dashboardで認証が有効になっているか確認
2. Email認証が有効になっているか確認
3. Confirm emailの設定を確認（開発環境では無効化推奨）

## 追加の検証（オプション）

### データベース直接確認

Supabase Dashboard > Table Editorで以下を確認：

1. `patients`テーブルに各ユーザーの`user_id`が正しく設定されている
2. `patient_records`テーブルに各記録の`user_id`が正しく設定されている
3. RLSポリシーが有効になっている（テーブルの設定で確認）

### SQL Editorでの確認

```sql
-- 全患者数を確認（管理者権限で実行）
SELECT COUNT(*) FROM patients;

-- ユーザーごとの患者数を確認
SELECT user_id, COUNT(*) as patient_count
FROM patients
GROUP BY user_id;

-- RLSポリシーの確認
SELECT * FROM pg_policies WHERE tablename = 'patients';
```

## まとめ

すべてのチェック項目が✅であれば、認可制御が正しく実装されています。

各ユーザーは自分のデータのみにアクセスでき、他のユーザーのデータには一切アクセスできないことが保証されます。
